# 明中都遗址探索游戏项目计划书（阶段汇报版）

> 项目名称：明中都遗址探索  
> 开发引擎：Cocos Creator 3.8.8  
> 目标平台：微信小游戏  
> 展示形式：横屏 2D 历史文化探索游戏  
> 当前阶段：核心玩法原型与首个地点模板基本完成  
> 文档用途：项目阶段汇报、现场演示与后续开发安排

---

## 一、项目概述

“明中都遗址探索”是一款以安徽凤阳明中都遗址及现实参观地点为基础的轻量历史探索游戏。项目希望将分散、距离较远的现实遗址转化为更适合移动端体验的数字空间，让玩家在较短时间内了解遗址整体格局，并进入重点地点进行近景探索。

游戏采用“大地图 + 地点分镜”的两级空间结构：

```text
开始界面
  ↓
俯瞰大地图：表现各地点的现实方位和道路联系
  ↓
地点近景：以实拍照片为构图基础，在固定透视画面中行走和交互
  ↓
现状 / 历史复原切换：对比遗址今天与历史时期的空间面貌
```

项目体验参考《蜡笔小新：煤炭镇的小白》中固定镜头、角色行走和场景切换的空间组织方式，但在题材、美术和内容上围绕明中都遗址进行原创设计，不复制原作角色与具体视觉资产。

## 二、项目背景与问题分析

### 2.1 现实参观的主要问题

- 明中都遗址范围较大，重点参观点之间距离较远。
- 有价值的展示内容较为分散，现实步行过程存在较长的内容空白。
- 部分遗址以地基、道路或环境遗存为主，普通游客难以直接想象历史空间。
- 实拍照片中存在游客、临时设施、光线和季节不统一等问题。

### 2.2 项目解决思路

- 用俯瞰大地图压缩地点之间漫长、重复的现实移动。
- 用照片透视场景保留真实地点的道路、建筑和空间关系。
- 用角色行走、地点切换和调查交互增强参与感。
- 用“遗址现状 / 历史复原”切换辅助玩家理解历史环境。
- 用统一的 AI 辅助美术流程清理照片并统一画面风格，同时保持空间布局可验证。

## 三、项目目标

### 3.1 总体目标

制作一款可在微信中便捷打开、操作门槛低、具有历史文化传播价值的遗址探索小游戏，形成“地图导览—地点探索—历史认知”的完整体验。

### 3.2 当前阶段目标

当前阶段优先建立可复用的技术与制作模板，而不是一次性完成所有地点：

1. 完成可行走的俯瞰大地图。
2. 完成大地图与地点场景的双向切换。
3. 完成一个地点的多分镜探索模板。
4. 完成人物四方向移动、透视缩放和摄像机跟随。
5. 完成可视化区域编辑扩展，降低后续场景制作成本。
6. 建立照片处理、风格审批和历史复原图制作流程。
7. 建立开始界面和微信小游戏构建入口。

## 四、核心设计方案

### 4.1 两级空间结构

| 层级 | 视角 | 主要功能 | 操作方式 |
|---|---|---|---|
| 俯瞰大地图 | 俯视 | 表现地点方位、道路关系和地点入口 | 摇杆或键盘沿道路移动 |
| 地点近景 | 固定照片透视 | 行走、调查、场景切换、现状与复原对比 | 摇杆或键盘自由移动 |

大地图不按照现实比例完整模拟步行，而是对距离进行适度压缩；地点内部则保留正常行走节奏，使玩家把时间集中在有内容的区域。

### 4.2 地点分镜结构

同一地点由多张具有明确连接关系的照片分镜组成。玩家走到门口、道路边缘或指定区域时，切换至另一张照片，并从对应出生点继续移动。

```text
入口桥 → 中轴道路 → 咖啡庭院 → 休闲广场
                     ↓
                展馆外院 → 王英雕像院落 → 室内展厅
```

这种方式既保留了现实照片的信息量，又避免制作完整 3D 场景带来的高成本。

### 4.3 现状与历史复原

地点场景预留“遗址现状 / 历史复原”切换。两种画面必须保持道路、可行走区、障碍区和出口位置基本一致，使切换前后角色位置和玩法逻辑不发生改变。

历史复原图遵循以下原则：

- 先保证原照片布局和透视关系，再进行建筑与环境重构。
- 历史建筑形制需要参考史料，避免将艺术想象当作确定事实。
- 对缺少依据的部分采用克制表达，并在展示内容中说明推测性质。
- 生成图必须经过人工审批后才能进入游戏。

## 五、技术路线

### 5.1 引擎与平台

- 使用 Cocos Creator 3.8.8，不更换引擎。
- 使用 TypeScript 编写运行时逻辑。
- 项目保持 2D 架构，降低微信小游戏包体与运行压力。
- 首发平台为微信小游戏，同时保留 Web Mobile 预览配置。
- 参考分辨率为 1280×720 横屏，并适配不同横屏比例。

### 5.2 移动与碰撞

- 大地图采用“拐点 / 交叉点 + 连线”的道路图结构。
- 玩家只能在道路形成的窄走廊内移动，不能任意穿过整张地图。
- 地点近景使用多边形定义可行走区和障碍区。
- 当前不使用完整 Box2D 动力学系统，而使用轻量几何计算，满足行走、边界和障碍阻挡需求。
- 入口检测同时考虑当前点与本帧移动线段，降低角色快速经过小入口时漏触发的概率。

### 5.3 照片透视

地点场景根据角色脚底的纵向坐标计算：

- 角色显示大小；
- 移动速度；
- 与背景的远近关系；
- 摄像机缩放和跟随位置。

因此角色在远处会更小、移动更慢，在近处会更大、移动更快，从而与照片透视保持一致。

### 5.4 数据与场景切换

- 大地图、路线、地点入口和地点分镜均采用配置驱动。
- 地点分镜的可行走区、障碍、交互区、切景区和出生点保存到 JSON。
- 切景区通过“目标分镜 + 目标出生点”建立连接。
- 大地图与地点场景之间保存入口状态，返回时角色落在对应道路位置。
- 开始新游戏时统一清理旧的地点调试与出生状态。

### 6.5 Cocos 编辑器扩展——已完成可用版本

已开发项目专用“明中都工具”扩展，支持：

- 打开大地图场景和刷新资源。
- 在不同照片分镜之间切换编辑背景。
- 创建规则 N 边形区域。
- 拖动顶点调整区域形状。
- 增加、删除顶点和删除区域。
- 设置可行走区、障碍区、交互区、切景区、遮挡区和出生点。
- 按统一命名规范管理区域节点。
- 为切景区选择目标分镜中的出生点。
- 设置返回大地图的入口 ID。
- 编辑透视最近点高度和视觉终线。
- 验证重复 ID、无目标切景和无效区域。
- 将编辑结果导出到 `regions.json`，供运行时直接读取。

该扩展使后续新增地点时主要调整背景图、区域顶点、障碍和进出口，不必重复编写场景移动代码。

## 七、当前可演示流程

汇报时建议按照以下顺序进行现场演示：

1. 展示古今双时空开始界面。
2. 点击“开始游戏”，播放画卷收拢动画。
3. 进入俯瞰大地图，使用摇杆控制现代游客移动。
4. 展示角色被约束在道路范围内，不能穿越非道路区域。
5. 走到游客中心入口，自动进入照片透视场景。
6. 在入口桥或中轴道路中前后移动，展示角色远小近大、远慢近快。
7. 切换游客中心的不同照片分镜，展示对应出生点衔接。
8. 展示障碍区阻挡效果和角色影子。
9. 展示“遗址现状 / 历史复原”切换接口。
10. 返回大地图，展示角色回到正确入口附近。
11. 最后打开 Cocos 扩展，演示拖动区域顶点和设置切景目标。

若现场时间有限，可重点演示“大地图—游客中心—分镜移动—返回大地图”这一条完整闭环。

## 八、阶段成果总结

目前项目已经从概念方案进入“可操作原型”阶段，完成的并非单张效果图，而是一套可以继续扩展的游戏框架：

- 已有完整的开始、地图、地点和返回流程。
- 已有可实际操作的现代人物和四方向动画。
- 已有符合照片透视的移动、缩放和摄像机逻辑。
- 已有多分镜场景切换与出生点系统。
- 已有可视化区域编辑工具。
- 已有图片生成、人工审批和素材接入流程。
- 已有微信小游戏构建配置。

这意味着后续新增地点时，不需要重新开发底层系统，而是可以将主要精力放在照片整理、区域标注、历史内容和互动设计上。

## 九、当前不足与待解决问题

### 9.1 内容不足

- 当前完成度主要集中在游客中心，其他遗址地点尚未形成完整照片分镜网络。
- 地点内还缺少正式调查物、NPC、对话和任务。
- 历史介绍文字、史料引用和文物信息尚未系统整理。

### 9.2 美术不足

- 当前部分背景仍属于风格验证图，细节一致性需要继续修整。
- 历史复原图存在地面反光过强等问题，需要二次生成或局部修图。
- 前景遮挡素材尚未正式切分和接入。
- 明朝人物形象及动画尚未制作完成。
- UI 字体、图标和音效仍为首版或预留状态。

### 9.3 技术验证不足

- 开始界面需要完成编辑器、Web Mobile 和微信小游戏三端回归测试。
- 微信开发者工具中的包体、纹理内存和加载速度尚需正式测量。
- 不同手机横屏比例、安全区域和触摸手感仍需真机测试。
- 大量地点图片接入后，需要验证资源分包、按需加载和释放策略。

| AI 生图改变真实布局 | 可行走区、出口和建筑位置失真 | 锁定原图构图，生成后与区域图逐项对照审批 |
| 历史复原依据不足 | 产生不准确的历史表达 | 区分史实、推测和艺术表现，引入资料审核 |
| 图片数量过多 | 微信包体和内存超限 | 分地点加载、压缩图片、退出场景后释放纹理 |
| 分镜连接复杂 | 玩家切景后方向混乱 | 使用命名统一的 Spawn 系统，并在扩展中验证链接 |
| 手机屏幕比例不同 | UI、入口和角色位置错位 | 使用归一化区域和横屏安全区适配 |
| 内容制作时间不足 | 技术完成但可玩内容少 | 优先完成游客中心精品样板，再复制模板扩展 |

## 十三、项目特色与创新点

1. **真实遗址与游戏空间结合**：不是简单展示照片，而是将现实地点转化为可行走、可切换的探索空间。
2. **大范围遗址的两级地图设计**：用俯瞰地图压缩距离，用照片分镜保留地点细节。
3. **照片透视角色系统**：角色大小、速度和摄像机随纵深变化，使 2D 角色自然进入现实照片。
4. **古今双时空对照**：同一布局下切换遗址现状与历史复原，帮助玩家理解空间变化。
5. **低成本可扩展生产工具**：通过 Cocos 区域编辑扩展，将新增地点转化为可视化配置工作。
6. **AI 生成与人工审批结合**：使用 AI 提升照片处理效率，同时通过布局约束和人工审批控制真实性。

## 十四、预期最终成果

- 一款可在微信中运行的横屏历史探索小游戏。
- 一张连接多个明中都重点地点的可行走俯瞰地图。
- 多个基于实拍照片的地点探索场景。
- 现代与明代两套角色或古今模式表现。
- 遗址现状与历史复原对比功能。
- 调查、对话、图鉴或轻任务系统。
- 一套可复用的照片场景制作和区域编辑工具。
- 一套包含原图、生成图、审批记录和历史依据的数字素材档案。

## 十五、汇报结语

当前项目已经验证了最关键的技术路线：现实遗址可以通过“俯瞰大地图 + 照片透视分镜”的方式转化为可操作的游戏空间。大地图、地点模板、角色移动、透视缩放、场景切换和编辑工具已经形成基础闭环。

下一阶段工作的重点将从“验证能不能做”转向“完善内容和提升表现”：以游客中心为精品样板，逐步扩展其他遗址地点，加入历史复原、调查交互和文化叙事，最终形成适合微信传播的明中都数字探索体验。

## 附录：三分钟汇报提纲

### 第一部分：为什么做（约 30 秒）

明中都遗址范围大、地点分散，现实参观中有较多重复步行和理解门槛。因此我们计划用微信小游戏把遗址整体地图、重点地点和历史复原结合起来，让用户以更轻量的方式认识明中都。

### 第二部分：怎么做（约 50 秒）

项目采用两级空间。地点之间使用俯瞰大地图，玩家通过摇杆沿道路移动；进入重点地点后，切换到基于实拍照片制作的固定透视场景。角色可以在照片地面中正常行走，并在远近移动时自动改变大小和速度。地点还可以在遗址现状与历史复原之间切换。

### 第三部分：已经完成什么（约 70 秒）

目前已完成开始界面、大地图道路移动、五类地点入口、游客中心七个照片分镜、分镜之间的出生点和切景、现代角色四方向动画、照片透视缩放、摄像机跟随和大地图返回逻辑。同时开发了 Cocos 编辑器扩展，可以直接创建和拖动可行走区、障碍、交互区、切景区和出生点，后续新增地点不需要重写底层代码。

### 第四部分：下一步做什么（约 30 秒）

下一步先稳定当前演示版本，再完善游客中心的前景、历史复原和调查交互；之后使用同一模板扩展西门、石墩、古井和午门等地点，最后进行微信真机测试和性能优化。
