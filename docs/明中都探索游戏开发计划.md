# 明中都遗址探索游戏开发计划

> 文档状态：开发基线 v1.0  
> 项目引擎：Cocos Creator 3.8.8  
> 首发平台：微信小游戏  
> 当前开发范围：俯瞰大地图  
> 暂不包含：地点内部行走、任务、对话、图鉴、AR、正式角色、美术批量生成

> **交互方案修订（2026-07-21）**：大地图不再采用“点击节点—自动沿路线快速移动”。正式方案改为玩家在大地图中使用虚拟摇杆自由移动，进入地点触发区后自动切入地点场景。本文后半部分保留的点击节点与寻路内容属于旧方案记录，不再作为实现依据；当前实现基线见《大地图首版实现说明.md》。

## 1. 项目定位

本项目是一款基于明中都现实遗址与实地照片制作的轻量历史探索游戏。玩家通过俯瞰地图在若干相距较远的地点之间快速移动，到达地点后再进入独立的近景探索场景。

现实遗址范围较大、可参观内容分散。如果完全按照现实比例模拟步行，玩家会把大量时间消耗在内容稀疏的路段。因此，游戏采用两级空间结构：

```text
俯瞰大地图
├─ 表达地点之间的真实方位与联系
├─ 负责选点、路线展示和快速移动
└─ 弱化漫长、重复的现实步行过程
    ↓
地点内部场景
├─ 使用基于现实照片生成的统一风格画面
├─ 角色正常行走
└─ 承载调查、交互、对话和任务
```

当前阶段只制作第一层“俯瞰大地图”。地点内部场景仅保留接口和占位信息，不在本阶段开发。

## 2. 已确定的设计决策

### 2.1 技术与平台

- 不更换引擎，继续使用 Cocos Creator 3.8.8。
- 首发目标为微信小游戏，而不是普通网页或原生 App。
- 项目保持 2D 架构，适合照片背景、UI、角色动画和轻量碰撞。
- 后续地点内部碰撞优先使用 Cocos Builtin 2D；不启用完整 Box2D 动力学模拟，除非未来玩法确实需要重力、弹性、关节或复杂刚体。
- 采用横屏显示。

### 2.2 空间结构

- 地点之间通过俯瞰地图快速移动。
- 地图节点暂以现有素材分组编号表示：`1`、`2`、`2.5`、`3`、`4`。
- 编号只是开发期 ID，正式名称待史料与展示内容确定后替换。
- 路线使用显式配置的连线与途经点，不根据卫星图自动寻路。
- 地点之间的连接关系不硬编码，后续可随路线设计调整。

### 2.3 画面来源

- 地点内部场景以实拍照片为结构依据。
- 不直接把原始照片作为最终游戏画面批量使用。
- 后续采用“照片参考生图”的方式统一美术风格，并处理游客、车辆、临时设施、杂乱构图、天气和色彩不统一等问题。
- AI 生成只负责视觉转绘和画面清理，不允许擅自补充未经考证的建筑形制、文物纹样或历史事实。
- 当前大地图可以先使用现有标注图作为位置参考，正式版本应使用无手绘标记的底图或重新绘制的俯瞰地图。

## 4. 大地图体验目标

大地图不是导航软件，也不承担精确测距。它需要同时完成四件事：

1. 让玩家知道几个地点在现实中的大致方位。
2. 让分散地点形成一个容易理解的整体结构。
3. 将漫长步行压缩为简洁、有氛围的快速移动。
4. 作为各地点场景的统一入口和返回中心。

体验关键词：清楚、轻量、平静、有方向感、避免等待。

## 5. 第一版大地图功能范围

### 5.1 必须完成

- 横屏大地图界面。
- 显示地点 `1`、`2`、`2.5`、`3`、`4`。
- 显示当前位置。
- 显示可到达地点与未开放地点的不同状态。
- 点击地点后显示地点信息卡片。
- 点击“前往”后，玩家标记沿配置路线移动。
- 移动过程中禁止重复操作。
- 抵达后更新当前位置。
- 抵达后触发地点进入事件；当前阶段进入占位页即可。
- 从占位页返回时，大地图保留上一次位置。
- 支持电脑鼠标调试和手机触摸操作。
- 适配微信小游戏横屏安全区域。

### 5.2 第一版不做

- GPS 定位与真实导航。
- 自动计算现实路线。
- 地图自由缩放与拖拽。
- 地点内部行走。
- 任务引导、NPC、对话和图鉴。
- 实际游戏时间或体力消耗。
- 联网账号、排行榜和多人功能。
- AR。
- 批量生成正式美术图。

## 6. 横屏布局方案

现有大地图接近方形，而目标设备为横屏手机。如果把地图强行拉伸铺满 16:9 屏幕，会造成地理结构变形；如果强制铺满并裁切，则容易丢失边缘地点。

推荐采用“地图主体 + 信息侧栏”布局：

```text
┌──────────────────────────────────────────┐
│ ┌──────────────────────┐ ┌────────────┐ │
│ │                      │ │ 地点名称   │ │
│ │      俯瞰地图        │ │ 地点简介   │ │
│ │                      │ │ 状态       │ │
│ │  节点、路线、玩家    │ │            │ │
│ │                      │ │  [前往]    │ │
│ └──────────────────────┘ └────────────┘ │
└──────────────────────────────────────────┘
```

- 设计参考分辨率：1280×720。
- 地图区域尽量保持原始宽高比，优先完整显示。
- 右侧区域用于地点名称、介绍、锁定条件和“前往”按钮。
- 刘海、圆角和系统手势区域由安全边距统一处理。
- 更宽屏幕增加两侧留白，不横向拉伸地图。
- 极窄设备允许略微缩小侧栏，但不遮挡节点。

## 7. 大地图交互流程

### 7.1 初次进入

```text
加载地图资源
→ 读取玩家地图状态
→ 将玩家标记放到默认地点
→ 显示当前地点信息
→ 进入可操作状态
```

默认地点暂不写死在程序里，由配置文件的 `initialLocationId` 决定。

### 7.2 选择地点

```text
点击地点节点
→ 节点高亮
→ 右侧显示地点信息
→ 判断是否已解锁、是否为当前位置、是否可到达
```

规则：

- 当前位置：按钮显示“进入地点”。
- 可到达地点：按钮显示“前往”。
- 未开放地点：按钮不可点击，并显示简短条件或“尚未开放”。
- 不与当前位置直接相连的地点：第一版可以配置完整多段路线；若路线不可达，则按钮不可点击。

### 7.3 快速移动

```text
点击“前往”
→ 锁定地图输入
→ 计算配置图中的路线
→ 玩家标记沿折线移动
→ 路过中间节点时不自动进入
→ 抵达目标节点
→ 更新并保存当前位置
→ 解锁输入
→ 显示“进入地点”
```

动画要求：

- 沿路线以近似恒定屏幕速度移动，不因线段长短产生明显忽快忽慢。
- 经过拐点时连续转向，不瞬移。
- 可加入轻微缩放、方向翻转或脚步动画，但不影响第一版完成。
- 移动时间应体现距离差异，但整体保持快速；单次移动不宜成为长时间等待。
- 移动中允许显示地点名称、简短提示或时间变化，第一版只保留接口。

### 7.4 进入地点

当前阶段没有正式地点场景，因此到达后的行为为：

```text
点击“进入地点”
→ 打开地点占位页
→ 显示地点 ID、临时名称和返回按钮
→ 点击返回
→ 回到大地图原位置
```

未来地点场景完成后，只替换“打开占位页”为“加载地点 Asset Bundle 并进入地点场景”，不修改大地图核心逻辑。

## 8. 地图状态机

地图必须使用明确状态，避免移动过程中重复点击造成路线和位置错乱。

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `Loading` | 加载地图与存档 | 不允许操作 |
| `Idle` | 地图等待选择 | 允许选择节点 |
| `Selected` | 已选择一个地点 | 允许取消、切换选择或前往 |
| `Moving` | 玩家标记正在移动 | 不允许再次选择或前往 |
| `Arrived` | 已抵达目标 | 允许进入地点或选择其他地点 |
| `Transitioning` | 正在切换地点页面 | 不允许操作 |
| `Error` | 配置或资源异常 | 显示错误并提供恢复入口 |

所有按钮是否可用，都应由当前状态统一决定，不能分散在多个脚本里各自判断。

## 9. 数据驱动设计

地图节点、路线和显示内容均从配置读取，避免把地点位置写死在 TypeScript 中。

### 9.1 地图配置示例

```json
{
  "mapId": "ming-zhongdu-main",
  "referenceSize": { "width": 922, "height": 985 },
  "initialLocationId": "location-1",
  "locations": [
    {
      "id": "location-1",
      "name": "地点一",
      "normalizedPosition": { "x": 0.09, "y": 0.55 },
      "sceneId": "location-1-scene",
      "defaultUnlocked": true,
      "description": "地点介绍待补充"
    },
    {
      "id": "location-2",
      "name": "地点二",
      "normalizedPosition": { "x": 0.45, "y": 0.28 },
      "sceneId": "location-2-scene",
      "defaultUnlocked": true,
      "description": "地点介绍待补充"
    }
  ],
  "routes": [
    {
      "id": "route-1-4",
      "from": "location-1",
      "to": "location-4",
      "bidirectional": true,
      "normalizedWaypoints": [
        { "x": 0.09, "y": 0.55 },
        { "x": 0.18, "y": 0.55 },
        { "x": 0.30, "y": 0.56 }
      ]
    }
  ]
}
```

### 9.2 使用归一化坐标

节点和路线点采用 `0–1` 的归一化坐标，而不是直接保存屏幕像素：

```text
实际 X = 地图显示宽度 × normalizedX
实际 Y = 地图显示高度 × normalizedY
```

这样在不同手机分辨率、地图缩放和编辑器预览尺寸下，地点仍能保持正确位置。

### 9.3 玩家地图存档

第一版只保存最少状态：

```json
{
  "currentLocationId": "location-1",
  "unlockedLocationIds": ["location-1", "location-4"],
  "visitedLocationIds": ["location-1"]
}
```

开发阶段使用本地存储。微信云存档和账号同步不在当前范围内，但存档访问应通过统一接口封装，避免未来替换时修改地图逻辑。

## 11. 路线图与寻路

第一版不在卫星底图上自动识别道路，而是把地点和路线组织成一个小型图结构：

```text
地点 = 图的节点
可通行路线 = 图的边
折线路径 = 边上的 waypoints
```

当目标地点不是直接相邻节点时，可使用简单的 Dijkstra 算法寻找总代价最小的路线。边的代价默认按屏幕路径长度计算，后续也可手动设置，用来表现某条路关闭、绕行或剧情限制。

路线设计要求：

- 路线必须经过现实中大致合理的道路方向。
- 视觉路线可以适度简化，不追求 GPS 精度。
- 每条路线必须有明确起点和终点。
- 双向路线通过 `bidirectional` 配置，不默认所有道路都能双向通行。
- 路线相交不代表自动连通；只有显式节点才产生转向关系。

## 12. 地点节点视觉状态

第一版至少需要以下状态：

| 状态 | 表现建议 |
|---|---|
| 未开放 | 降低饱和度、锁图标、不可前往 |
| 已开放 | 正常图标，可选择 |
| 当前地点 | 明显光环或旗标 |
| 已访问 | 增加小型印章或完成标记 |
| 当前选中 | 放大、描边或呼吸效果 |

节点图标应与底图形成足够对比，并提供比图标本身更大的透明点击范围，避免手机上难以点中。

第一版只需要临时图标，不在程序结构中绑定最终美术尺寸和样式。

## 13. 简单 Cocos 编辑器扩展计划

地图第一版可以先通过配置和场景组件完成。行为稳定后，再加入项目级简单扩展，减少后续调整成本。

扩展暂定目录：

```text
extensions/ming-map-tools
```

建议功能：

1. “创建大地图场景”——生成标准节点结构与必要组件。
2. “同步地图配置”——根据 JSON 创建或更新地点节点。
3. “导出节点位置”——把场景中拖动后的节点位置写回归一化配置。
4. “验证地图”——检查重复 ID、缺失地点、断开的路线、无效出生点和越界坐标。
5. “显示路线调试”——在编辑器中显示所有折线和方向。

扩展不承担运行时逻辑，也不在第一步开发复杂面板。优先确保地图本身可运行，再根据实际编辑痛点补充工具。

## 14. 后续照片生图流程

照片生图属于地点场景美术生产流程，不在当前大地图阶段执行，但现在先确定原则，避免后续风格和资产失控。

### 14.1 目标

- 保留真实地点的镜头结构、道路、遗迹位置和辨识特征。
- 统一季节、天气、光照、色彩和笔触。
- 清理游客、车辆、遮挡、临时展棚和其他干扰元素。
- 增强画面的层次感与适合角色行走的空间感。
- 建立原创的国风动画视觉语言，而不是复制某个现有游戏或动画 IP 的具体画风。

### 14.2 基本流程

```text
原始照片归档
→ 判断用途与镜头质量
→ 标记必须保留的真实结构
→ 清理或遮罩不需要的元素
→ 使用统一风格参考进行图生图
→ 对照原片检查结构偏差
→ 历史与场地准确性审核
→ 手工修整
→ 裁切与分层
→ 输出游戏尺寸
→ 导入 Cocos
```

### 14.3 风格基线

正式批量生成前，先选择一张代表性照片制作“黄金样张”。黄金样张确定：

- 线条粗细与清晰程度。
- 植被、砖石、天空和水面的表现方式。
- 色彩饱和度与明暗范围。
- 写实程度与卡通化程度。
- 角色与背景预计的融合方式。
- 是否保留摄影透视和镜头畸变。

黄金样张通过后，其他照片以同一套风格说明和参考图生成，不逐张临时决定风格。

### 14.4 真实性约束

每张图需保留一份生成记录：

```text
源照片路径
地点 ID
画面用途
必须保留元素
允许移除元素
禁止生成元素
使用的风格参考
提示词版本
生成版本
审核结果
最终输出路径
```

对于遗址、建筑复原和文物图案，必须把“艺术处理”和“历史复原”区分开。没有可靠资料时，只能美化现实遗址画面，不能把推测内容表现成确定事实。

### 14.5 输出与性能

- 4096×3072 原图作为母版和生成参考保存，不直接批量进入微信小游戏。
- 根据实际屏幕占用尺寸输出游戏版本。
- 同一地点的大图归入独立 Asset Bundle，按需加载。
- 图像格式、尺寸和压缩率在微信开发者工具及真机对比后确定。
- 场景退出后释放不再使用的大图纹理，避免连续游览导致内存累积。

## 16. 分阶段实施顺序

### M1：地图静态骨架

交付内容：

- 大地图场景。
- 横屏布局和安全区域。
- 临时底图。
- 五个地点节点。

### M2：路线与移动

交付内容：

- 路线配置结构。

- 节点连通图。
- 路径选择。
- 玩家标记沿折线移动。

### M3：地图状态与占位地点

交付内容：

- 本地地图存档。
- 当前地点、已解锁、已访问状态。
- 地点占位页。
- 进入和返回流程。
- 异常配置保护。

验收：关闭并重新打开后仍能恢复当前位置；进入占位地点再返回时地图状态正确。

交付内容：

验收：微信环境中可以完成“选择地点—快速移动—进入占位页—返回地图”的完整流程。

### M5：地图编辑工具

只有在 M1–M4 的结构稳定后实施。

交付内容：

- 项目级 Cocos 地图工具扩展。
- 同步、导出和验证功能。
- 地图配置使用说明。

验收：新增或调整地点时，不需要修改地图运行时代码。

## 18. 风险与处理策略

| 风险 | 影响 | 处理策略 |
|---|---|---|
| 现有大地图带手绘标记 | 不适合作为正式画面 | 仅作参考，正式节点和路线动态绘制 |
| 方形地图与横屏比例冲突 | 拉伸或裁切导致信息丢失 | 地图主体加右侧信息栏，保持原比例 |
| 地点正式名称未确定 | UI 与配置反复修改 | 开发期使用稳定 ID，名称作为可替换文本 |
| 路线关系后续变化 | 硬编码导致返工 | 数据驱动图结构，不写死连接 |
| 照片数量和尺寸较大 | 微信包体与内存压力 | 地点 Bundle、按需加载、真机压缩测试 |
| 图生图改变真实结构 | 导览可信度下降 | 必保元素标注、原图对照、人工审核 |
| 批量生成风格漂移 | 场景不统一 | 先做黄金样张，再固定风格基线 |
| 过早开发任务和地点内容 | 基础流程变化导致返工 | 当前只完成地图闭环，后续逐层扩展 |

## 19. 后续待确认事项
